    Как устроен CineFlow

    Здесь всё про ваш проект простыми словами: из каких частей он состоит, что за что отвечает, где это лежит в коде, что показать на защите и что сказать вслух. Знать Spring заранее не нужно.

    Весь проект в одном абзаце

    CineFlow — сайт сети кинотеатров, разрезанный на маленькие программы — микросервисы. Каждая отвечает за своё: фильмы, бронирование, цены, оплата, пользователи, бар, уведомления. Пользователь общается только с Gateway — он раскидывает запросы по нужным сервисам. Сервисы находят друг друга через Eureka, а настройки получают из Config Server.

    Spring за 15 минут

    Минимум, без которого код проекта не читается. Учить Spring целиком не нужно: достаточно понимать, что значат метки с собачкой @.

    Три слова, которые надо знать

    Spring Boot

    Каркас для серверных программ на Java. Сам запускает веб-сервер, подключается к базе, читает настройки. Программист пишет только логику и помечает классы аннотациями.

    Spring Cloud

    Набор дополнений к Spring Boot специально для микросервисов: Config Server, Eureka, Gateway, Circuit Breaker, OpenFeign. Это и есть тема задания.

    Аннотация

    Метка над классом или методом, начинается с @. Говорит Spring, что это такое и что с ним делать. Например, @GetMapping("/movies") значит «этот метод отвечает на адрес /movies».

    Как устроен один сервис внутри

    Все сервисы проекта устроены одинаково, в четыре слоя. Запрос проходит их сверху вниз:

    СлойЧто делаетПример из movie-service
    ControllerПринимает HTTP-запрос и отдаёт ответ в JSONCatalogController
    ServiceБизнес-логика: считает, проверяет, собирает данныеCatalogService
    RepositoryДостаёт и сохраняет данные в базеMovieRepository
    EntityКласс, который соответствует таблице в базеMovie → таблица movies

    Вот так выглядит контроллер. Метод movies() срабатывает, когда браузер открывает /api/movies:

    @RestController                 // этот класс отвечает на HTTP-запросы
@RequestMapping("/api")          // все адреса начинаются с /api
public class CatalogController {

    @Operation(summary = "Фильмы в прокате в городе")   // описание для Swagger
    @GetMapping("/movies")                              // GET /api/movies
    public List<MovieView> movies(@RequestParam(required = false) Long cityId) {
        return catalog.moviesInCity(cityId);                 // передаём в слой Service
    }
}

    movie-service/src/main/java/ru/cineflow/movie/web/CatalogController.java

    А репозиторий — вообще одна строка. Методы findAll(), save(), findById() Spring пишет сам, SQL не нужен:

    public interface MovieRepository extends JpaRepository<Movie, Long> {}

    Словарик аннотаций проекта

    Нажми на аннотацию, чтобы увидеть, где она встречается.

    @SpringBootApplication

    Точка входа сервиса: «запусти тут Spring Boot». Есть в каждом сервисе, например MovieServiceApplication.java.

    @RestController, @GetMapping, @PostMapping

    Класс принимает HTTP-запросы, а методы отвечают на конкретные адреса. GET — получить данные, POST — отправить (например, купить билет: @PostMapping("/checkout") в BookingController).

    @Service

    Класс с бизнес-логикой. Например, CheckoutService оформляет покупку билета.

    @Entity

    Класс — это таблица в базе данных. Поля класса — колонки. Например, Movie, Ticket.

    @FeignClient

    Позволяет вызвать другой сервис как обычный метод Java. @FeignClient(name = "payment-service") — Feign сам спросит у Eureka адрес payment-service и отправит HTTP-запрос. Файлы в booking-service/.../client/.

    @CircuitBreaker

    Предохранитель на вызове другого сервиса. Если сервис часто падает, вызовы временно прекращаются и сразу срабатывает запасной метод (fallbackMethod). Файл Remote.java в booking-service.

    @KafkaListener

    Метод, который подписан на «ящик» в Kafka и вызывается при новом сообщении. Например, в TicketEventsListener user-service начисляет бонусы за купленный билет.

    @EnableConfigServer, @EnableEurekaServer

    Одна строка, которая превращает обычное приложение в Config Server или Eureka Server. Вся остальная работа уже написана внутри Spring Cloud.

    @ConfigurationProperties

    Переносит настройки из yml-файла в поля класса. PricingProperties получает правила цен из config-repo/pricing-service.yml.

    @Value

    Подставляет одну настройку в поле. Например, ключ Claude API в AssistantLlm.

    Два файла, которые есть у каждого сервиса

    pom.xml

    Список библиотек, которые нужны сервису. Например, строка spring-cloud-starter-netflix-eureka-client подключает регистрацию в Eureka. Maven скачивает их при сборке.

    application.yml

    Настройки: порт, имя сервиса, адрес базы. В вашем проекте у сервисов там почти пусто — всё остальное приходит из Config Server.

    1

    Минимум 3 микросервиса

    Простыми словами. Микросервис — отдельная маленькая программа со своей задачей, своим портом и своей базой данных. Вместо одного большого сайта у вас 7 программ, которые общаются между собой по HTTP.

    СервисПортОтвечает заСвоя база
    movie-service8081Города, кинотеатры, фильмы, сеансы, отзывыmovie_db
    booking-service8082Места, бронь, покупка, билеты, ассистент, админкаbooking_db + Redis
    pricing-service8083Цены и промокодыpricing_db
    payment-service8084Оплата (учебная, без настоящих денег)нет
    user-service8085Регистрация, вход, бонусы, привязка Telegramuser_db
    concession-service8086Бар: попкорн и напитки к креслуconcession_db
    notification-service8087Письма и сообщения в Telegramнет

    Плюс три служебных сервиса Spring Cloud (Config Server, Eureka, Gateway) и Telegram-бот на Python.

    Как показать

    Открыть Eureka: http://localhost:8761. Там список всех запущенных сервисов в статусе UP.

    Скажи так

    «Наш проект — 7 бизнес-микросервисов и 3 инфраструктурных сервиса Spring Cloud. У каждого бизнес-сервиса своя задача и своя база данных — это паттерн Database per Service. Сервисы общаются по HTTP через OpenFeign и асинхронно через Kafka».

    Зачем каждому сервису своя база?

    Чтобы сервисы не зависели друг от друга. Можно поменять структуру таблиц в одном сервисе и не сломать остальные. Если база одного сервиса упадёт, другие продолжат работать.

    Чем микросервисы лучше одного большого приложения (монолита)?

    Каждый сервис можно обновлять, перезапускать и масштабировать отдельно. Падение одного не роняет весь сайт. Минус — сложнее: нужны Eureka, Gateway, Config, чтобы всё это связать. Как раз это и есть Spring Cloud.

    2

    Spring Cloud Config

    Простыми словами. Настройки всех сервисов лежат в одной папке config-repo. Отдельный сервис, Config Server, раздаёт их остальным. При запуске каждый сервис говорит: «я pricing-service, дай мои настройки» — и получает их по HTTP.

    Где в коде

    Сервер — одна аннотация:

    @SpringBootApplication
@EnableConfigServer          // всё, это уже Config Server
public class ConfigServerApplication { ... }

    config-server/src/main/java/ru/cineflow/config/ConfigServerApplication.java

    Каждый сервис знает только своё имя и адрес Config Server:

    spring:
  application:
    name: pricing-service                         # по имени выберется pricing-service.yml
  config:
    import: "configserver:http://config-server:8888"

    В config-repo лежат application.yml (общее для всех: Eureka, Kafka, база, логи) и файл для каждого сервиса: pricing-service.yml, gateway.yml и так далее.

    Как показать

    1. Открыть http://localhost:8889/pricing-service/default (у тебя Config Server на порту 8889). Это ровно тот ответ, который получает pricing-service при запуске. Примерно такой:

    { "name": "pricing-service", "profiles": ["default"],
  "propertySources": [
    { "name": "file:/config-repo/pricing-service.yml",
      "source": { "pricing.banner": "Осенний марафон: −20% ...", "pricing.center-coefficient": 1.3, ... } },
    { "name": "file:/config-repo/application.yml", "source": { ... } } ] }

    2. Главный фокус — изменение на лету. В VS Code открыть config-repo/pricing-service.yml, поменять banner или center-coefficient, сохранить. На сайте: Админка → Конфигурация → Обновить конфигурацию. Бегущая строка и цены поменялись, сервис не перезапускали.

    Скажи так

    «Все настройки вынесены в одно место — папку config-repo. Config Server раздаёт их сервисам по HTTP: каждый при запуске запрашивает свои настройки по имени. Главный плюс — настройки можно менять без изменения кода и даже без перезапуска: вызываем /actuator/refresh, и сервис подтягивает новые значения».

    Почему настройки в папке, а не в git-репозитории?

    Используется профиль native — так проще запускать локально. В реальном проекте обычно указывают git-репозиторий: тогда у настроек есть история изменений. Переключается одной настройкой.

    Что будет, если Config Server упадёт?

    Уже запущенные сервисы продолжат работать: настройки они получили при старте. Не запустятся только новые — у них стоит fail-fast: true, и они будут ждать Config Server до 40 попыток.

    Как именно сервис обновляет настройки без перезапуска?

    Кнопка в админке вызывает POST /actuator/refresh у pricing-service. Spring заново скачивает настройки с Config Server и перезаполняет класс PricingProperties, помеченный @ConfigurationProperties.

    3

    Eureka

    Простыми словами. Телефонная книга сервисов. Каждый сервис при запуске записывается в Eureka: «я movie-service, мой адрес такой-то». Потом каждые 5 секунд отмечается, что жив. Когда кому-то нужен movie-service, его адрес берут из Eureka, а не прописывают руками.

    Где в коде

    @SpringBootApplication
@EnableEurekaServer          // реестр сервисов
public class EurekaServerApplication { ... }

    eureka-server/src/main/java/ru/cineflow/eureka/EurekaServerApplication.java

    Клиенты подключают библиотеку spring-cloud-starter-netflix-eureka-client, а адрес Eureka берут из общего config-repo/application.yml. После этого к сервису можно обращаться по имени: lb://movie-service или @FeignClient(name = "movie-service"). Буквы lb значат load balancer: если копий сервиса несколько, запросы распределятся между ними.

    Как показать

    Открыть http://localhost:8761 — скриншот выше, в первом пункте. Бонус для эффекта: запустить вторую копию бронирования командой docker compose --profile scale up -d booking-service-2. Через минуту в Eureka у BOOKING-SERVICE станет 2 экземпляра, и Gateway начнёт делить запросы между ними.

    Скажи так

    «Eureka — реестр сервисов. Каждый сервис при запуске регистрируется в ней и раз в 5 секунд сообщает, что жив. Gateway и другие сервисы обращаются друг к другу не по адресу, а по имени, например lb://movie-service, а адрес берут из Eureka. Поэтому можно запустить несколько копий сервиса, и нагрузка распределится автоматически».

    Что будет, если сервис упадёт?

    Он перестанет отмечаться. Через 15 секунд Eureka уберёт его из списка, и на него перестанут слать запросы.

    Что за красная надпись про SELF PRESERVATION?

    Режим самосохранения специально выключен в настройках Eureka, чтобы упавшие сервисы быстрее пропадали из списка. Для учебного проекта и демонстрации это удобнее.

    4

    API Gateway

    Простыми словами. Единая дверь в систему на порту 8080. Браузер и бот знают только этот адрес. Gateway смотрит на путь запроса и пересылает его нужному сервису: /api/movies → movie-service, /api/booking → booking-service. Сам сайт (HTML, CSS, JS, постеры) тоже раздаёт Gateway.

    Где в коде

    Маршруты — в настройках, а не в Java-коде:

    - id: movie-service
  uri: lb://movie-service                          # куда: адрес из Eureka
  predicates: [ "Path=/api/movies/**,/api/sessions/**,..." ]   # какие пути
  filters:
    - name: CircuitBreaker                         # предохранитель на маршруте
      args: { name: movieRoute, fallbackUri: forward:/fallback/movie-service }

    config-repo/gateway.yml

    Ещё в Gateway есть RequestLoggingFilter (логирует каждый запрос) и общая страница Swagger для всех сервисов.

    Как показать

    Открыть http://localhost:8080/api/movies: придёт JSON со списком фильмов. Браузер обратился к Gateway, а ответил movie-service. Потом показать файл gateway.yml с маршрутами.

    Скажи так

    «Все запросы приходят на Spring Cloud Gateway, порт 8080. По пути запроса он определяет нужный сервис и находит его адрес через Eureka. На Gateway же сделано общее: Circuit Breaker на каждом маршруте, логирование всех запросов и сводная документация API. Клиенту не нужно знать, сколько у нас сервисов и где они находятся».

    Зачем Gateway, если можно ходить в сервисы напрямую?

    Один адрес для клиента; общие вещи (защита от сбоев, логи, безопасность) делаются один раз, а не в каждом сервисе; сервисы можно переносить и масштабировать, клиент этого не заметит.

    Почему у Gateway библиотека webflux, а не обычная?

    Spring Cloud Gateway реактивный: он не держит поток на каждый запрос, а обрабатывает их асинхронно. Поэтому один Gateway выдерживает много одновременных запросов.

    5

    Circuit Breaker дополнительное

    Простыми словами. Предохранитель, как в электрощитке. Если сервис начал падать, мы перестаём к нему обращаться и сразу отдаём запасной ответ, вместо того чтобы долго ждать и копить ошибки. Через время проверяем: ожил ли.

    CLOSEDВсё хорошо, запросы идут в сервис.
    OPENБольше половины из последних запросов упали. 15 секунд запросы в сервис не отправляются, сразу работает запасной вариант.
    HALF_OPENПробуем 2 запроса. Прошли — снова CLOSED, нет — снова OPEN.

    Где в коде

    В проекте Resilience4j стоит в двух местах.

    На Gateway, на каждом маршруте (код выше). Если сервис не отвечает, Gateway отдаёт ответ из FallbackController, а сайт показывает заглушку:

    В booking-service, на вызовах других сервисов:

    @CircuitBreaker(name = "payment", fallbackMethod = "payFallback")
public PaymentResult pay(PaymentRequest req) { return payments.pay(req); }

public PaymentResult payFallback(PaymentRequest req, Throwable t) {  // запасной метод
    throw new PaymentUnavailableException(t);   // дальше сработает компенсация
}

    booking-service/src/main/java/ru/cineflow/booking/client/Remote.java

    Правила срабатывания — в config-repo/booking-service.yml: окно 10 запросов, порог 50% ошибок, 15 секунд в OPEN.

    Как показать

    1. Войти как admin@cineflow.ru / admin123, открыть Админка → Хаос и Circuit Breaker.
    2. Нажать «Упал» — платёжный сервис начинает отвечать ошибкой.
    3. Попробовать купить билет. Деньги не списаны, места остались за зрителем, бонусы вернулись. Повторить попытку 3–4 раза: предохранитель считает минимум 4 вызова. На панели payment переходит в OPEN.
    4. Нажать «Работает». Через 15 секунд HALF_OPEN, потом CLOSED.
    Скажи так

    «Circuit Breaker на Resilience4j защищает систему от каскадных сбоев. Если сервис отвечает ошибками больше чем в половине случаев, предохранитель размыкается, и 15 секунд запросы туда не идут — сразу срабатывает запасной сценарий. Например, если упала оплата, заказ откатывается: бонусы возвращаются, места остаются за зрителем. Потом предохранитель пробует снова и, если сервис ожил, замыкается».

    Чем это отличается от обычного try/catch?

    try/catch каждый раз честно пытается позвонить и ждёт таймаута. Circuit Breaker запоминает статистику и при частых сбоях вообще перестаёт звонить в упавший сервис: пользователь сразу получает ответ, а больной сервис не добивают лишней нагрузкой.

    Что такое сага и компенсация?

    Покупка — цепочка шагов в разных сервисах: цены, бар, списание бонусов, оплата. Если шаг посередине упал, уже сделанные шаги отменяются обратными действиями. Например, списанные бонусы возвращаются. Это в CheckoutService.

    6

    Мониторинг и логирование дополнительное

    Простыми словами. Actuator — библиотека, которая добавляет каждому сервису служебные адреса: жив ли он, сколько памяти ест, в каком состоянии предохранители. Логи — журнал событий каждого сервиса.

    Где в коде

    Actuator подключён во всех 10 сервисах, а открытые адреса указаны в общем config-repo/application.yml:

    management:
  endpoints:
    web:
      exposure:
        include: health,info,metrics,refresh,env,loggers,circuitbreakers,...

    Логи пишутся в консоль и в папку logs/, по файлу на сервис. Gateway логирует каждый запрос и выдаёт ему номер X-Request-Id:

    [a1b2c3d4] GET /api/movies → movie-service | 200 OK | 35 мс

    gateway/src/main/java/ru/cineflow/gateway/RequestLoggingFilter.java

    Как показать

    • http://localhost:8082/actuator/health — состояние booking-service: база, Redis, предохранители. Ответ вида {"status":"UP","components":{"circuitBreakers":...,"db":...,"redis":...}}.
    • http://localhost:8082/actuator/circuitbreakers — состояние всех предохранителей.
    • http://localhost:8082/actuator/metrics — список метрик.
    • Логи Gateway: docker compose logs gateway --tail 20 или файл logs/gateway.log.
    Скажи так

    «В каждом сервисе подключён Spring Boot Actuator: по адресу /actuator/health видно, жив ли сервис и его зависимости — база, Redis, Circuit Breaker'ы. Логи каждого сервиса пишутся в консоль и в файл. Gateway логирует каждый запрос: метод, путь, сервис, статус и время ответа, и присваивает запросу уникальный X-Request-Id, чтобы найти его в логах».

    Зачем X-Request-Id?

    Один запрос пользователя проходит через несколько сервисов. По одинаковому номеру можно найти его следы во всех логах и понять, где именно произошла ошибка.

    Документация API дополнительное

    Простыми словами. Swagger — автоматически созданная страница со списком всех адресов сервиса: что принимает, что возвращает. Прямо на ней можно отправить запрос и посмотреть ответ.

    Где в коде

    В каждом сервисе библиотека springdoc-openapi. Она сама читает контроллеры и строит описание. Аннотации @Operation(summary = "...") и @Tag добавляют человеческие подписи. В Gateway собрана общая страница с выпадающим списком всех 7 сервисов (настройка springdoc.swagger-ui.urls в gateway.yml).

    Как показать

    Открыть http://localhost:8080/swagger-ui.html, вверху справа выбрать сервис, например movie-service. Раскрыть GET /api/movies → Try it out → Execute. Внизу появится настоящий ответ сервиса.

    Скажи так

    «Документация генерируется автоматически библиотекой springdoc по стандарту OpenAPI. У каждого сервиса есть своё описание, а на Gateway собрана общая страница Swagger UI для всех сервисов. Прямо из неё можно отправить запрос и увидеть ответ».

    Что такое OpenAPI?

    Стандарт описания API в формате JSON. Каждый сервис отдаёт такое описание по адресу /v3/api-docs, а Swagger UI рисует по нему удобную страницу.

    Путь одного билета

    Лучший способ понять микросервисы — проследить одну покупку от клика до сообщения в Telegram. В ней участвуют почти все части проекта.

      Скажи так

      «Покупка билета — это сага из нескольких сервисов. booking-service по очереди обращается через Feign к pricing, concession, user и payment. Если какой-то шаг падает, уже сделанное откатывается. После успешной оплаты событие уходит в Kafka, и дальше user-service начисляет бонусы, а notification-service рассылает билет на почту и в Telegram — уже без участия booking-service».

      Остальные фишки

      Этого нет в обязательных требованиях, но об этом точно спросят, потому что это видно на сайте.

      Kafka — ящик для записок между сервисами

      Один сервис кладёт сообщение «произошло вот это», другие забирают и реагируют. Отправитель не ждёт ответа. В проекте два «ящика» (топика):

      • ticket-events — «билет куплен / возвращён / отсканирован». Кладёт booking-service, читают user-service (бонусы 5/7/10%) и notification-service (билет на почту и в бот).
      • notifications — «сообщи человеку». Кладут booking (напоминание о сеансе, лист ожидания), concession (заказ из бара готов), user (код для смены пароля). Читает notification-service.
      Скажи так

      «Kafka — брокер сообщений для асинхронного общения. Покупка не ждёт, пока уйдут письма, и не ломается, если бот выключен: сообщения полежат в Kafka. А чтобы добавить новый сервис, например аналитику, достаточно подписать его на топик, booking-service менять не нужно».

      Redis — временное удержание мест

      Когда зритель выбирает кресло, booking-service записывает в Redis ключ hold:сеанс:ряд-место с командой SET NX («записать, только если ключа ещё нет») и временем жизни 5 минут. Если двое нажали на одно кресло одновременно, записать получится только у одного. Через 5 минут ключ исчезает сам, и место освобождается.

      booking-service/src/main/java/ru/cineflow/booking/service/SeatService.java

      Скажи так

      «Чтобы два человека не купили одно место, удержание сделано в Redis атомарной командой SET NX с TTL 5 минут. На демо со 100 ботами видно: конфликтов десятки, а двойных продаж ноль».

      WebSocket — живой зал

      Обычно браузер спрашивает сервер, а сервер отвечает. WebSocket — постоянное соединение, по которому сервер сам присылает новости. Поэтому, когда кто-то выбирает кресло, у всех остальных оно сразу становится занятым, а ещё видны курсоры других зрителей. Сделано на STOMP в booking-service (WebSocketConfig), Gateway пробрасывает путь /ws/**.

      PostgreSQL — базы данных

      Один сервер PostgreSQL, но внутри пять отдельных баз: movie_db, booking_db, pricing_db, user_db, concession_db (создаются в infra/postgres/init.sql). Таблицы создаёт сам Spring (JPA) по классам с @Entity.

      Docker Compose — всё одной командой

      Файл docker-compose.yml описывает все 14 контейнеров: базы, Kafka, Redis, почту и все Java-сервисы. У каждого Java-сервиса свой Dockerfile: сначала Maven собирает jar, потом он запускается на Java 21. Команда docker compose up -d поднимает всё сразу и в правильном порядке: сервисы ждут, пока будут готовы Config Server, Eureka и база.

      Telegram-бот

      Отдельная программа на Python (библиотека aiogram), лежит в папке cineflow-bot. Своей базы у неё нет: она ходит в тот же API через Gateway, что и сайт. Уведомления получает от notification-service по HTTP на порт 8090. Привязка аккаунта: сайт даёт ссылку t.me/бот?start=link_КОД, бот передаёт код и номер чата в user-service.

      Скажи так

      «Бот — ещё один клиент нашего API, как сайт. Один бэкенд, два интерфейса».

      Киноассистент

      Работает в booking-service на правилах, без нейросети. Разбирает вопрос на условия (жанр, день, время, количество мест, бюджет), по ключевым словам понимает намерение (найти сеанс, посоветовать фильм, рассказать о фильме, ответить про сайт) и обращается к другим сервисам. Помнит контекст, поэтому понимает «а завтра?». Если в .env есть ключ Claude API, непонятные вопросы уходят нейросети.
